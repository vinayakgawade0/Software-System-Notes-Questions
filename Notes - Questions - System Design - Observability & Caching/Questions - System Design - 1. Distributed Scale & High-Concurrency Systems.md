## Distributed Transactions: Two-Phase Commit vs Saga Pattern

### Two-Phase Commit Protocol Mechanics

### Limitations of Two-Phase Commit at Microservice Scale

#### Can you explain the Two-Phase Commit protocol, why it is considered an anti-pattern in modern microservices, and how the Saga pattern resolves its limitations?

> **Direct Answer:** The Two-Phase Commit (2PC) protocol is a synchronous, coordinator-driven protocol designed to enforce ACID transactions across distributed databases by splitting execution into a Prepare (voting) phase and a Commit (execution) phase. In modern microservices, 2PC is considered an anti-pattern because it relies on blocking pessimistic row locks across network boundaries, introduces a single point of failure at the coordinator, and causes throughput collapse under latency or network partitions. The Saga pattern resolves these limitations by abandoning synchronous global locks in favor of eventual consistency, breaking the transaction into independent, immediately committed local transactions coordinated via events and compensated via backward-compensating transactions upon downstream failures.

> **Key Nuance / Trade-off:** While Sagas eliminate the blocking locks and availability bottlenecks of 2PC, they introduce data isolation anomalies (dirty reads, non-repeatable reads) because intermediate state is committed and visible to other transactions. Architects must design compensating transactions to be strictly idempotent, commutative, and resilient to out-of-order event delivery, often using state-machine orchestrators or outbox patterns.

## Online Ticketing Architecture: High-Concurrency & Read-Heavy Scale

### Core Architectural Constraints and Domain Decoupling

### Relational Schema Design for Strict Booking Integrity

### Distributed Concurrency Control and Double-Booking Prevention

#### How would you design the architecture for a massive online ticketing system like BookMyShow, specifically focusing on concurrency and high-throughput reads?

> **Direct Answer:** A massive online ticketing architecture decouples read-heavy browsing from write-heavy booking domains to accommodate extreme (100:1 to 1000:1) read-write skew, deploying a high-availability catalog tier backed by CDN and Redis caching alongside a strictly consistent RDBMS booking engine. Concurrency is handled through a two-tier locking strategy: temporary seat reservation using atomic Redis distributed locks with a 5-minute Time-To-Live (TTL), backed by database-level pessimistic row locking (`SELECT ... FOR UPDATE`) during final payment commitment. High-throughput read performance is maintained by caching materialized seat maps as bitmasks or JSON in Redis, while surge traffic during flash sales is throttled via token-bucket rate limiters and virtual waiting rooms at the API Gateway.

> **Key Nuance / Trade-off:** Relying solely on Redis locks risks phantom bookings or double-allocations during node failovers or network partitions; therefore, the relational database `SELECT ... FOR UPDATE` acts as the definitive safety net. Furthermore, holding pessimistic database locks must be constrained strictly to the final payment authorization phase rather than the entire checkout flow to prevent thread pool exhaustion and relational database deadlocks.

## URL Shortener Architecture: Algorithmic Design & Distributed Storage

### Core Requirements and Capacity Estimation

### Base62 Encoding Algorithmic Core

#### How would you design a highly scalable URL shortening system like Bitly, and what is the optimal algorithmic approach for generating the short links?

> **Direct Answer:** A highly scalable URL shortener is designed as a read-heavy (100:1), distributed key-value lookup system using distributed NoSQL storage (Cassandra or DynamoDB) fronted by an in-memory Redis cluster with LRU eviction. The optimal algorithmic approach for generating short links is Base62 encoding (utilizing `[a-z, A-Z, 0-9]`), where a 7-character token provides over 3.52 trillion unique combinations ($62^7$). To eliminate hash collisions and database round-trip checks, unique tokens are pre-generated by a standalone Key Generation Service (KGS) or converted from 64-bit distributed counters (Snowflake IDs), delivering $O(1)$ write operations.

> **Key Nuance / Trade-off:** Choosing between HTTP 301 and 302 redirects represents a fundamental architectural trade-off: HTTP 301 enables client browser caching, drastically slashing backend server load and bandwidth costs but completely blinding the system to click analytics. Commercial systems overwhelmingly use HTTP 302 redirects to guarantee that every click hits the backend for analytics collection, monetization, and abuse detection, despite the increased server infrastructure load.
