# Observability - Chapter 2: Distributed Tracing, Monitoring & Logging

## Distributed Tracing: Request Flow and Context Propagation

### Core Tracing Mechanics: Trace ID, Span ID, and Span Trees

In microservice ecosystems, a single user transaction often cascades across dozens of independent services, API gateways, message queues, and relational or NoSQL databases. When an endpoint encounters an unexpected latency spike or transient failure, standard server logs fail to identify the offending service. Distributed tracing reconstructs the complete lifecycle of a request across network boundaries into a correlated, visual execution DAG (Directed Acyclic Graph).

```
[ Client Request ]
       |
       v
+---------------------------------------------------------------------------------+
| API Gateway (Span 1: Root Span)                                                 |
| Trace ID: 4bf92f3577b34da6a3ce929d0e0e4736                                      |
| Span ID:  00f067aa0ba902b7  | Parent ID: null                                    |
+---------------------------------------------------------------------------------+
       |
       v  (HTTP Header: traceparent)
+---------------------------------------------------------------------------------+
| Order Service (Span 2: Child Span)                                              |
| Trace ID: 4bf92f3577b34da6a3ce929d0e0e4736                                      |
| Span ID:  5fb397be34d23b0f  | Parent ID: 00f067aa0ba902b7                        |
+---------------------------------------------------------------------------------+
       |                                                 |
       v  (HTTP Header: traceparent)                     v  (JDBC Driver Interceptor)
+---------------------------------------+         +-------------------------------+
| Payment Service (Span 3: Child Span)  |         | PostgreSQL (Span 4: Child)    |
| Span ID:  a2d3c4e5f6071829            |         | Span ID:  99b8a7c6d5e4f321    |
| Parent ID: 5fb397be34d23b0f           |         | Parent ID: 5fb397be34d23b0f   |
+---------------------------------------+         +-------------------------------+
```

#### Core Distributed Tracing Primitives

1. **Trace ID:**
   * A globally unique 16-byte (128-bit) or 8-byte hexadecimal string generated by the edge component (API Gateway or ingress reverse proxy) that first handles the request.
   * Remains completely immutable across the entire distributed call graph.
2. **Span ID:**
   * An 8-byte (64-bit) identifier representing a single contiguous unit of execution (e.g., executing an HTTP GET request, executing an SQL query, or processing a message off Kafka).
3. **Parent Span ID:**
   * References the Span ID of the caller component, allowing visualization engines to assemble a nested execution tree displaying precise latency waterfalls.
4. **Span Attributes & Events:**
   * Key-value metadata attached to individual spans (e.g., `http.status_code=500`, `db.statement="SELECT * FROM orders WHERE id = ?"`, exception stack traces).

### Network Context Propagation: W3C TraceContext and B3 Specifications

To maintain tracing continuity across decoupled services, tracing metadata must be propagated across inter-service transport protocols (HTTP headers, gRPC metadata, Kafka message headers).

#### Standard Propagation Formats

* **W3C TraceContext (Universal CNCF Standard):**
  * The modern standard adopted by OpenTelemetry, AWS, GCP, and Azure.
  * Uses the standardized HTTP header `traceparent`:
    ```http
    traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
    ```
    * `00`: Protocol version.
    * `4bf92f3577b34da6a3ce929d0e0e4736`: 16-byte Trace ID.
    * `00f067aa0ba902b7`: 8-byte Parent Span ID.
    * `01`: Trace flags (`01` indicates the trace was sampled for persistent recording).
* **B3 Propagation Specification (Zipkin Heritage):**
  * Widely used in Spring Cloud Sleuth (Spring Boot 2.x) and early Envoy deployments.
  * Propagated via multiple HTTP headers:
    * `X-B3-TraceId: 4bf92f3577b34da6`
    * `X-B3-SpanId: 00f067aa0ba902b7`
    * `X-B3-Sampled: 1`

When Service A invokes Service B via HTTP client (Spring `RestClient`, WebClient, Feign, or OkHttp), the tracing instrumentation automatically intercepts the outgoing request and injects these headers. On the receiving end, the ingress interceptor extracts the headers and establishes the child span context.

### OpenTelemetry Standard and Vendor-Neutral Instrumentation

Historically, software organizations suffered severe vendor lock-in by embedding vendor-specific SDKs (Datadog dd-trace, New Relic Agent, AppDynamics) directly into their application dependencies. Migrating observability providers required comprehensive code rewrites and dependency updates.

```
+-------------------------------------------------------------------------+
|                  Application Code (Zero Vendor APIs)                    |
|                Uses OpenTelemetry (OTel) API / SDK                      |
+-------------------------------------------------------------------------+
                                    |
                        (OTLP / Protobuf Protocol)
                                    v
+-------------------------------------------------------------------------+
|                  OpenTelemetry (OTel) Collector Daemon                  |
|    - Ingests Telemetry via OTLP (Traces, Metrics, Logs)                 |
|    - Buffers, Batches, Attributes Enrichment, Tail Sampling             |
+-------------------------------------------------------------------------+
       |                                     |                      |
  (Exporters)                           (Exporters)            (Exporters)
       v                                     v                      v
+--------------+                      +--------------+       +--------------+
| Jaeger /     |                      | Datadog /    |       | Prometheus / |
| Grafana Tempo|                      | AWS X-Ray    |       | Grafana Loki |
+--------------+                      +--------------+       +--------------+
```

#### The OpenTelemetry (OTel) Paradigm

* **Unified API & SDK:** OpenTelemetry, an open-source project incubated under the Cloud Native Computing Foundation (CNCF), unifies tracing, metrics, and logging into a single vendor-agnostic standard.
* **Write Once, Export Anywhere:** Applications instrument their code exclusively against standard OTel abstractions or leverage zero-code automated bytecode injection (`opentelemetry-javaagent.jar`).
* **The OpenTelemetry Collector:** Telemetry is streamed over standard OpenTelemetry Protocol (OTLP/gRPC) to an out-of-process collector. The collector can enrich, sample, filter, and fan-out telemetry to any backend (Jaeger, Zipkin, Datadog, Honeycomb, Dynatrace) entirely via YAML configuration without touching application source code.

### Telemetry Sampling Strategies: Head-Based vs Tail-Based Sampling

In high-throughput microservice architectures generating hundreds of thousands of requests per second, recording 100% of all traces is economically and technically prohibitive. It saturates network interface cards (NICs), creates massive I/O bottlenecks, and triggers catastrophic vendor ingestion bills.

| Strategy | Ingestion Mechanism | Benefits | Critical Vulnerabilities |
| :--- | :--- | :--- | :--- |
| **Head-Based Sampling** | Sampling decision is made at the very ingress of the request (e.g., API Gateway) before work begins (e.g., sample exactly 5% of traffic). | Extremely lightweight; requires zero memory buffering. Downstream services simply check the `traceparent` sample bit (`01` vs `00`) and skip collection if unselected. | **Blinded to Incidents:** If a rare 500 error or 10-second database deadlock occurs within the 95% of non-sampled requests, no trace data is recorded. Engineers cannot debug the incident. |
| **Tail-Based Sampling** | Sampling decision is deferred until the entire request transaction completes across all services. | **100% Incident Visibility:** Telemetry pipelines retain 100% of HTTP 5xx errors, exceptions, and latency outliers (> 1500ms), while aggressively dropping routine 200 OK fast requests. | **Infrastructure Overhead:** Requires an intermediate tier (such as the OpenTelemetry Collector) to buffer full traces in memory until all spans arrive before making the sampling verdict. |

### Log Correlation via Mapped Diagnostic Context and Spring Boot 3 Micrometer

Tracing reveals **where** latency or failure occurred in the distributed network; structured logs explain **why** by capturing domain state, parameters, and stack traces. Without explicit correlation, searching through millions of log lines across dozens of containers during an outage is futile.

#### Mapped Diagnostic Context (MDC) Mechanics

The industry standard connects traces to logs by injecting the active `traceId` and `spanId` into thread-local storage via SLF4J / Logback Mapped Diagnostic Context (MDC).

In Spring Boot 3, **Micrometer Tracing** (the successor to Spring Cloud Sleuth) automatically populates the MDC during HTTP request execution, reactive pipeline steps, and message consumption.

#### Configuration and Implementation

##### 1. Spring Boot Configuration (`application.yml`)

```yaml
management:
  tracing:
    sampling:
      probability: 1.0   # 100% sampling in dev; tune to 0.10 (10%) in prod
    propagation:
      type: W3C          # Enforces W3C traceparent standard
  zipkin:
    tracing:
      endpoint: "http://otel-collector:4318/v1/traces"
```

##### 2. Logging Pattern Configuration (`logback-spring.xml`)

```xml
<?xml version="1.0" encoding="UTF-8"?>
<configuration>
    <appender name="STDOUT" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <!-- Injects [traceId,spanId] automatically from MDC -->
            <pattern>%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] [%X{traceId:-},%X{spanId:-}] %-5level %logger{36} - %msg%n</pattern>
        </encoder>
    </appender>

    <root level="INFO">
        <appender-ref ref="STDOUT"/>
    </root>
</configuration>
```

##### 3. Generated Log Output

```text
2026-11-26 21:14:02.104 [http-nio-8080-exec-3] [4bf92f3577b34da6a3ce929d0e0e4736,00f067aa0ba902b7] INFO  c.e.service.OrderService - Validating order for customer: 84920
2026-11-26 21:14:02.340 [http-nio-8080-exec-3] [4bf92f3577b34da6a3ce929d0e0e4736,00f067aa0ba902b7] ERROR c.e.service.OrderService - Payment reservation failed: Insufficient funds
```

When an engineer inspects a slow or failed trace in Grafana, Datadog, or Jaeger, they can click a single button to execute a pre-filtered log query across Elasticsearch or Loki using the captured `traceId`, instantly isolating all log events across all microservices for that single transaction.

## Real-Time Microservice Monitoring: The Three Pillars and Golden Signals

### The Three Pillars of Distributed Observability: Metrics, Logs, and Traces

Modern distributed software operations abandon legacy host-level monitoring in favor of holistic **Distributed Observability**.

```
                           +---------------------------------------+
                           |       Distributed Observability       |
                           +---------------------------------------+
                                 /            |                                            /             |                                            v              v              v
                       +-------------+ +-------------+ +-------------+
                       |   Metrics   | |    Logs     | |   Traces    |
                       | (The "What")| | (The "Why") | |(The "Where")|
                       +-------------+ +-------------+ +-------------+
```

| Pillar | Underlying Telemetry Nature | Optimal Use Case | Primary Tooling |
| :--- | :--- | :--- | :--- |
| **Metrics (The "What")** | Aggregable, numeric time-series data indexed by key-value label sets. Extremely lightweight in storage and network footprint. | Detecting anomalies, building real-time dashboards, auto-scaling clusters, triggering automated alerting thresholds. | Prometheus, VictoriaMetrics, M3DB, Grafana |
| **Logs (The "Why")** | Timestamped, structured or unstructured textual records emitted during discrete code execution events. | Root-cause analysis, capturing detailed business state, recording exceptions, forensic investigation. | Fluent Bit, Promtail, Elasticsearch, Grafana Loki |
| **Traces (The "Where")** | End-to-end distributed execution paths traversing network topologies with precise latency waterfall breakdowns. | Pinpointing network bottlenecks, identifying slow database queries, understanding cross-service dependency graphs. | OpenTelemetry, Jaeger, Zipkin, Grafana Tempo |

### Prometheus Pull-Based Metrics Architecture and Scrape Mechanics

Prometheus serves as the cloud-native industry standard for metrics storage and alerting. Unlike legacy systems that rely on agents pushing metrics out to centralized servers, Prometheus implements a **Pull-Based (Scraping) Model**.

```
+--------------------------------------------------------------------------------+
|                         Kubernetes / Service Discovery                         |
+--------------------------------------------------------------------------------+
                                           |
                           (Discovers Target Pod IPs)
                                           v
+--------------------------------------------------------------------------------+
|                       Prometheus Server (Pull Engine)                          |
|  - Scrapes endpoints periodically (e.g., scrape_interval: 15s)                 |
|  - Stores in Time-Series Database (TSDB) on disk                               |
|  - Evaluates AlertManager rules                                                |
+--------------------------------------------------------------------------------+
       |                                           |
  (HTTP GET)                                  (HTTP GET)
       v                                           v
+-------------------------------+           +-------------------------------+
| Microservice A Pod            |           | Microservice B Pod            |
| http://10.244.1.15:8080/      |           | http://10.244.2.32:8080/      |
|        actuator/prometheus    |           |        actuator/prometheus    |
+-------------------------------+           +-------------------------------+
```

#### Why Pull Over Push?

1. **Self-Protecting Ingestion:** Under sudden traffic surges, services pushing metrics can DDoS their own monitoring cluster. In a pull architecture, Prometheus scrapes at an invariant, controlled schedule (e.g., every 15 seconds), completely decoupling application traffic spikes from monitoring ingestion load.
2. **Simplified Health & Liveness Detection:** If Prometheus fails to scrape an endpoint, it immediately records the target as `up == 0`. In push architectures, distinguishing between an application that crashed and one that is simply idle requires complex dead-man switches.
3. **Decoupled Architecture:** Application instances do not require configuration specifying where the monitoring backend lives. They simply expose a standard endpoint (e.g., Spring Boot Actuator's `/actuator/prometheus`).

### Alerting on the RED Method: Rate, Errors, and Duration

A ubiquitous operational failure in microservice operations is alerting on resource symptoms (e.g., CPU utilization > 85% or Memory usage > 80%). High CPU utilization is often completely normal during batch processing or high traffic, and auto-scalers handle it gracefully. Alerting on symptoms results in alert fatigue and burned-out engineering teams.

Senior systems architects configure actionable production alerts strictly around the **RED Method** (developed by Tom Wilkie), representing real user experience:

```
+-----------------------------------------------------------------------------+
|                             The RED Method                                  |
+-----------------------------------------------------------------------------+
| R - Rate     : Number of requests per second served by the application.     |
| E - Errors   : Percentage of requests resulting in HTTP 5xx failures.       |
| D - Duration : Time taken to process requests (focusing on p95 / p99).      |
+-----------------------------------------------------------------------------+
```

#### PromQL Implementation Examples

1. **Request Rate (RPS):**
   ```promql
   sum(rate(http_server_requests_seconds_count[2m])) by (service)
   ```
2. **Error Ratio (Alert if > 1% over 5 minutes):**
   ```promql
   sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
   /
   sum(rate(http_server_requests_seconds_count[5m])) * 100 > 1.0
   ```
3. **p95 Latency Duration (Alert if p95 > 1000ms):**
   ```promql
   histogram_quantile(0.95, sum(rate(http_server_requests_seconds_bucket[5m])) by (le)) > 1.0
   ```

If CPU spikes to 95% but Error Rate remains 0% and Duration remains well within the SLA, the on-call engineer should never be paged.

### The High Cardinality Trap in Time-Series Datastores

In Prometheus and other time-series databases (TSDBs), **cardinality** refers to the total number of unique time-series created by permutations of label keys and values.

#### The Mathematical Trap

Every unique combination of label key-value pairs instantiates a distinct, independent time-series stream stored in RAM:

$$\text{Total Streams} = \prod_{i=1}^{n} |\text{Unique Values of Label } i|$$

If an engineer adds dynamic, user-level attributes as metric labels:
```promql
# FATAL ANTI-PATTERN: High Cardinality Label
http_requests_total{service="payment", user_id="849204", order_id="93012948"}
```
With 1,000,000 users and 500,000 orders, this single metric generates hundreds of billions of individual time-series streams. The Prometheus TSDB memory pool is instantly exhausted, inducing persistent heap thrashing, disk thrashing, and unrecoverable Out-Of-Memory (OOM) crashes.

#### Golden Rules for Label Cardinality

* **Permitted in Metrics (Low Cardinality):** Enum-like, bounded values (`http_method=GET|POST`, `status_code=200|404|500`, `region=us-east-1`).
* **Strictly Prohibited in Metrics (High Cardinality):** User IDs, Order IDs, UUIDs, email addresses, IP addresses, full URL paths with dynamic path variables.
* **Where High Cardinality Belongs:** High cardinality data belongs exclusively in **Logs** (Elasticsearch/Loki) and **Trace Span Attributes** (Jaeger/Tempo), where search architectures are explicitly designed for high-entropy tokens.

### The Indexing Tax: Elasticsearch (ELK) vs Grafana Loki (PLG)

When choosing a persistent logging backend, engineering teams balance rich search functionality against infrastructure operating cost.

```
+-------------------------------------------------------------------------------+
| Elasticsearch (ELK): The "Indexing Tax" Approach                              |
| Ingest Log ---> Tokenize Every Word ---> Build Massive Inverted Index         |
| Result: Sub-second arbitrary text search, but huge RAM and disk overhead.     |
+-------------------------------------------------------------------------------+

+-------------------------------------------------------------------------------+
| Grafana Loki (PLG): The Label-Only Approach                                   |
| Ingest Log ---> Index Only Labels (app, env) ---> Compress Raw Text to S3     |
| Result: Drastically lower RAM/storage costs; uses parallel grep for text.    |
+-------------------------------------------------------------------------------+
```

| Dimension | The ELK Stack (Elasticsearch, Logstash, Kibana) | The PLG Stack (Promtail, Loki, Grafana) |
| :--- | :--- | :--- |
| **Indexing Strategy** | Full-text inverted index. Parses and indexes every single word, token, and field inside the JSON payload. | **Label-only indexing.** Indexes only stream metadata labels (e.g., `app=order-service`, `env=prod`). Log bodies remain raw compressed chunks. |
| **Storage Architecture** | Requires persistent high-speed SSD blocks (e.g., AWS EBS) mounted to stateful Elasticsearch cluster nodes. | Stores compressed log chunks directly in cheap distributed object storage (Amazon S3, Google Cloud Storage, MinIO). |
| **Operational & Financial Cost** | **High Indexing Tax:** Demands heavy JVM heap allocations, dedicated cluster management, and massive storage volumes at terabyte scale. | **Extremely Cost-Efficient:** Consumes a fraction of RAM and CPU; storage costs are slashed by 75–85% via S3 tiering. |
| **Query Performance** | Blindingly fast arbitrary unstructured full-text keyword searches across petabytes of historical logs. | Extremely fast when scoped by labels; slower on full-string scans across vast time horizons because it executes brute-force parallelized streaming greps. |
| **Best Architectural Fit** | Enterprise security auditing, compliance log parsing, complex multi-attribute SIEM analysis. | Cloud-native Kubernetes microservice architectures where developers query logs in conjunction with Prometheus metrics. |

### OpenTelemetry Collector as a Universal Telemetry Router

Operating heterogeneous telemetry agents inside application containers increases memory footprint and ties microservices to specific monitoring providers. The **OpenTelemetry (OTel) Collector** eliminates this by acting as an in-cluster proxy and universal router.

```
                                    +-----------------------------------------+
                                    |        OpenTelemetry Collector          |
                                    |                                         |
+--------------------+              |  [ Receivers ]                          |
| App 1 (OTel SDK)   | -- OTLP ---> |  - otlp (gRPC :4317 / HTTP :4318)       |
+--------------------+              |                                         |
                                    |  [ Processors ]                         |
+--------------------+              |  - memory_limiter                       |
| App 2 (OTel SDK)   | -- OTLP ---> |  - batch                                |
+--------------------+              |  - tail_sampling (drop 200s, keep 500s) |
                                    |  - attributes (strip sensitive PII)     |
                                    |                                         |
                                    |  [ Exporters ]                          |
                                    +-----------------------------------------+
                                         /              |                                                      /               |                                                      v                v                v
                                 +------------+   +------------+   +------------+
                                 | Prometheus |   |  Datadog   |   |   Jaeger   |
                                 +------------+   +------------+   +------------+
```

#### Key Capabilities of the OTel Collector Pipeline

1. **PII Masking & Data Sanitization:** Strips credit card numbers, passwords, and authorization tokens from logs and span attributes before data leaves the Kubernetes VPC.
2. **Cost-Optimization & Tail Sampling:** Buffers spans and executes intelligent filtering (e.g., dropping noisy health check logs `/actuator/health` and keeping 100% of exception traces).
3. **Zero-Code Backend Migration:** Switching the organization from Jaeger to Grafana Tempo or Datadog requires changing only the `exporters` block in the Collector YAML configuration, with zero modifications to application code.

### Build vs Buy: Self-Hosted Infrastructure vs Managed SaaS Cost Control

A major architectural dilemma for engineering leadership is deciding whether to operate a self-hosted open-source monitoring stack or purchase an enterprise SaaS observability solution:

```
+-----------------------------------------------------------------------------------+
| Self-Hosted (Prometheus + Loki + Jaeger + Grafana)                                |
| Pro: Zero data licensing fees, complete data sovereignty within VPC.             |
| Con: Requires dedicated SRE engineers to scale TSDBs, manage disks, handle HA.   |
+-----------------------------------------------------------------------------------+

+-----------------------------------------------------------------------------------+
| Managed SaaS (Datadog, Splunk, Honeycomb, Dynatrace)                              |
| Pro: Turnkey setup, zero maintenance, integrated correlation out of the box.     |
| Con: Ingest-based billing models cause sudden, astronomical monthly bills.       |
+-----------------------------------------------------------------------------------+
```

#### Senior Architect Ingestion Cost Management

When enterprise organizations select SaaS platforms (such as Datadog), bills often spiral out of control due to unbounded data ingestion rates. Senior architects tame these costs using the OpenTelemetry Collector:

* **Aggressive Edge Filtering:** Dropping all `DEBUG` and `TRACE` log levels at the cluster collector level before egress.
* **Metrics Aggregation:** Computing metric rollups and histograms inside the collector and forwarding only the aggregated summaries to the SaaS provider.
* **Intelligent Span Sampling:** Discarding high-frequency, low-value trace spans (e.g., repetitive Redis cache hits or health check polling) while retaining all multi-service business transactions.
